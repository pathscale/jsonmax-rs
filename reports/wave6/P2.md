## DOM changes

`DomScratch` retains its reusable container stack and now owns a vector of `DepthKeys` tables indexed by container depth. Each table holds reusable open-addressed slots, its live length, and a generation counter. Entries contain the cooked hash plus `Span32`/`SpanSource`, directly referencing raw payload bytes for unescaped keys or the existing decoded arena for escaped keys. No separate key bytes, pointers into growing arenas, or tape lookups are needed for duplicate comparisons.

Closing an object resets its table by incrementing the generation and setting live length to zero. Sibling objects reuse the same slots; parent objects keep their independent generation while descendants execute. Hash collisions compare complete cooked bytes, with a length check before comparison. Growth rehashes only entries in the active generation. Generation wrap physically clears the table once per 2^32 generations, preventing stale slots from becoming live again. Error cleanup invalidates remaining live generations before another input can reuse scratch storage. `duplicate_capacity()` now reports the sum of retained per-depth slot capacities, preserving its meaning as a slot count rather than bytes.

After `BlockCursor::new` validates input admission, a cold tape reserves `(raw.len() / 8).clamp(16, 262_144).min(limits.max_payload_bytes as usize)` words. Existing tape capacity is reused without another input-size-based reservation, so longer strings do not force unnecessary warm growth when their tape shape still fits. Growth remains fallible and checked against u32 addressing.

Tape append/reservation helpers are marked `#[inline(always)]`. Compact unescaped ASCII keys and strings take an early straight-line one/two-word append path. A capacity check bypasses fallible reservation machinery when space already exists. Array values reuse the byte already found by the container loop rather than calling `skip_whitespace` again. Grammar, count, numeric and depth checks remain in place.

The additive `Node::unescaped_key_token()` and `Node::unescaped_string_token()` accessors (also exposed in `navigate`) return the original quoted slice only for genuine native handles whose record is unescaped. They support both compact ASCII and extended Unicode/large records. Their construction guarantee comes from immutable native documents; no arbitrary caller-provided span is accepted as trusted JSON.

## Native encoding changes

Owned and borrowed entry points share the optimized `write_tape_view` implementation. Before emitting, it reserves `raw.len().min(limits.max_output_bytes)` bytes and preallocates writer frames from the document's validated maximum depth. Reservation and emission failures both return frames to `WriterScratch` and preserve the original error.

Unescaped member names and string values use their original quoted raw slices directly, without UTF-8 validation or escape discovery. Private writer methods still enforce the decoded byte limit (`token.len() - 2`), surrounding syntax, object/array counts, commas, colons, output budget and poisoning. Each quoted token is emitted as one slice. Escaped strings and keys still resolve their trusted cooked content and use the existing single-pass `EscapePositions` SIMD-mask writer with minimal escaping.

Native numbers already had the requested private `trusted_number_lexeme` path at P2 entry. It remains in use: native spelling is emitted directly after `max_number_bytes` checking, without `raw::validate`. Public arbitrary number lexemes, legacy tables and raw fragments retain their existing validation paths.

`LimitedSink` now separates its actual reserved capacity endpoint (`capacity_len`) from the pending token endpoint (`reserved_len`). An upfront capacity hint must not count as a pending token suffix: otherwise every subsequent escape would grow the whole hint and falsely fail an exact output limit. Reservations reuse the capacity hint while pending escape growth tracks only the current token. Every write still checks limits and external sink lengths; external reservation/write errors retain their metadata and poison the writer.

For a conforming initially empty vector sink, the raw-input upper bound permits one output-buffer allocation for successful native encoding. Container frames are a separate allocation on cold scratch, now reserved once, and remain reusable. This is an implementation expectation pending coordinator measurement, not a claim that total cold encoding allocates only once. A sink can reject the upfront reservation before any output is written, including when it would otherwise accept smaller incremental writes.

## Coordinator verification and limitations

Run the owned crate suites after P1/P2/P3 finish, for example `cargo test -p jmax-dom -p jmax-encode`, then the workspace/feature/no_std gates and sequential allocation/throughput harnesses. No such command has been executed by P2. The new tests and cross-crate type checking remain unverified until that barrier.

Warm zero-allocation reuse requires recycling borrowed documents or retaining owned scratch results and sufficient capacity at every used depth. New widths/depths or escaped output can still grow storage. Cold tape preallocation is a bounded heuristic, not a universal two-allocation guarantee; dense or very large documents can grow further. It may reserve excess tape for long strings. Output reservation may retain whitespace/escape slack up to the encoder ceiling and exposes sink reservation failures earlier. Ordinary object close is O(1); the explicit generation-wrap fallback is O(table capacity). Arbitrary caller-created NodeId membership resolution remains unchanged.
